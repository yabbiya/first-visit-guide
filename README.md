# First Visit Notes (먼저 다녀온 메모)

> **Not just a quiet day — a quiet day when it's actually open.**
> Closed days, bookings, entry rules and tricky spots for Korea's top sights, on one screen — in English, 中文, 日本語 (and 한국어).

한국을 여행하는 외국인을 위한 "처음 가는 곳" 안내 웹앱. 장소마다 흩어진 출입 필수 정보(휴무·예약·입장 조건),
헤매기 쉬운 곳, 붐빔, 날씨를 "내 상황에 맞는 순서"로 한 화면에 보여준다.
처음에는 한국인 길치·아이 동반 가족용으로 시작했고, 2026-11-01에 외국인 여행자 중심으로 방향을 바꿨다(아래 개발 기록).

**사이트**: https://first-visit-korea-guide.vercel.app

## 실행 방법 (내 컴퓨터)

```bash
npm run build   # 장소 파일 형식 검사 + 장소 목록(places/index.json) + 검색용 페이지(/en/… 등)·sitemap.xml 만들기
npm start       # 내 컴퓨터 안에서만 열리는 작은 웹서버 켜기
```

브라우저에서 `http://localhost:8000`을 연다. 서버를 끌 때는 터미널에서 `Ctrl + C`를 누른다.
(`index.html`을 더블클릭해서 열면 브라우저 보안 때문에 장소 파일을 못 읽는다.)

### 날씨 인증키 넣기
1. [공공데이터포털](https://www.data.go.kr)에서 **기상청_단기예보 조회서비스**를 활용 신청한다.
2. 마이페이지 → 데이터활용 → Open API → 활용신청 현황에서 **일반 인증키(Decoding)**를 복사한다.
3. 프로젝트 폴더의 `.env.example`을 복사해서 이름을 `.env`로 바꾸고, `KMA_SERVICE_KEY=` 뒤에 키를 붙여넣는다.
4. 서버를 껐다가(`Ctrl + C`) 다시 `npm start`로 켠다. 터미널에 "날씨 인증키: 설정됨"이 나오면 성공이다.

발급 직후에는 키가 등록되기까지 1~2시간 걸릴 수 있다. 그동안 날씨 칸에는 "키 등록 대기 중"이 표시된다.
`.env`는 비밀 파일이라 깃허브에 올라가지 않는다(`.gitignore`에 등록돼 있음).

### 결제($5 평생 이용권) 켜는 순서
지금은 `premium.json`의 잠글 기능 목록이 비어 있어서 **모든 기능이 무료**이고, 구매 창도 보이지 않는다.
결제를 켤 때는 아래 순서대로 한다. 1~4는 Lemon Squeezy 누리집에서 직접 하고, 비밀번호·계좌 정보는 코드에 넣지 않는다.

1. [Lemon Squeezy](https://www.lemonsqueezy.com)에 가입하고 가게(Store)를 만든다. 정산 받을 계좌·세금 정보를 넣는다.
2. 상품(Product)을 만든다: 가격 **$5, 한 번 결제(Single payment)**, 이름 예: "First Visit Notes — Lifetime pass".
3. 상품 설정에서 **License keys를 켜고**, 기기 수 제한(Activation limit, 예: 3)과 기한 없음(Unlimited)을 고른다.
   환불 기간도 정한다(예: 14일). 이 숫자를 `refund.html`의 `[REFUND DAYS]`에 똑같이 적는다.
4. 숫자 두 개와 링크 하나를 복사한다.
   - Store ID (Settings → Stores), Product ID (상품 화면 주소나 상세 정보)
   - 결제 링크 (상품의 Share → Checkout URL, `https://….lemonsqueezy.com/buy/…`)
5. Vercel → 프로젝트 → Settings → Environment Variables에 `LEMONSQUEEZY_STORE_ID`, `LEMONSQUEEZY_PRODUCT_ID`를 넣는다.
   (남의 상품 키로 열리는 것을 막는 데 쓴다. 이름은 `.env.example`에 있다.)
6. `terms.html`, `refund.html`, `privacy.html`의 `[CONTACT EMAIL]`, `[REFUND DAYS]` 빈칸을 채운다.
7. `premium.json`에 결제 링크(`checkoutUrl`)와 잠글 기능(`features`)을 넣는다. 잠글 수 있는 기능:
   - `"mustgo"`: "오늘은 꼭 가야 해요" 모드
   - `"quiet-days"`: 붐빔 칸의 "덜 붐비는 날" 추천 (오늘 붐빔 정도는 계속 무료)
   ```json
   { "features": ["mustgo"], "checkoutUrl": "https://….lemonsqueezy.com/buy/…" }
   ```
8. `npm run build`. 6번 빈칸이 남아 있으면 검사가 막고 어느 페이지의 어느 빈칸인지 알려준다.

### 검색엔진에 사이트 알리기 (배포 후 한 번)
`npm run build`가 언어·장소별 페이지(`/en/gyeongbokgung/` 등)와 `sitemap.xml`을 만든다. 배포한 뒤 아래를 한 번 한다.
1. [Google Search Console](https://search.google.com/search-console)에서 "URL 접두어"로 `https://first-visit-korea-guide.vercel.app/`를 등록한다.
   소유 확인은 "HTML 태그" 방식을 고르고, 나오는 `<meta name="google-site-verification" …>` 한 줄을 알려주면 `index.html`에 넣는다.
2. 확인되면 왼쪽 "Sitemaps"에 `sitemap.xml`을 제출한다.
3. [Bing Webmaster Tools](https://www.bing.com/webmasters)는 "Google Search Console에서 가져오기"로 한 번에 등록할 수 있다.
4. (선택) 일본 Yahoo는 구글 검색 결과를 쓰고, 중국 바이두는 중국 내 서버·등록이 필요해 이번 범위에서 뺀다.

## 장소 추가하는 방법

> 먼저 **[장소 품질 기준](docs/place-quality.md)**을 읽는다. 조사 체크리스트 8가지, 신뢰도 표시, 쓰는 규칙이 있다.

1. `places/` 안에 장소 이름으로 폴더를 만든다 (영문 소문자와 `-`만, 예: `seoul-forest`).
2. [docs/place-template.json](docs/place-template.json)을 그 폴더에 `place.json`으로 복사해서 채운다. `id`는 폴더 이름과 같아야 한다.
3. 첫 화면 카테고리를 `categories`에 적는다([places/categories.json](places/categories.json)에 있는 것, 여러 개 가능).
   지역별 보기의 지역을 `area`에 하나 적는다([places/areas.json](places/areas.json)의 id, 예: `"central-seoul"`).
   맞는 지역이 없으면 areas.json에 새 지역을 추가한다(4개 언어 이름 필수, 외국인이 아는 이름으로 — 구 이름은 쓰지 않는다).
   꼭 알아야 할 한 줄이 있으면 `notice`(14자 이내, 예: "후원 예약 필요")에 적는다. 쉬는 요일은 카드에 자동으로 붙는다.
4. 체크리스트 8가지를 조사하고 결과를 `checked`에 적는다 (메모 id / "해당 없음" / "확인 못함" / "기본 정보에 표시").
5. 사진이 있으면 그 폴더의 `photos/` 안에 넣고, 메모의 `photos`에 `file`, `caption`, `credit`을 적는다.
6. `npm run build`를 실행한다. 틀린 곳이나 빠진 체크리스트 항목이 있으면 한국어로 알려준다.

**쓸 때 주의할 점**
- 요약 문장은 따로 쓰지 않는다. 화면의 "꼭 기억할 3가지"는 메모 중 지금 상황에서 가장 중요한 3개의 **제목**으로
  자동으로 만들어진다. 그래서 **제목만 읽어도 핵심이 전달되게** 쓴다 (예: "정발산역 1번 출구로 나오세요").
- 메모끼리 같은 내용을 반복하지 않는다. 한 사실은 한 카드에만 쓴다.
- 없으면 방문 목적 자체를 못 이루는 정보(신분증, 예약 확인, 출입 절차 등)는 **제목에 쓰고 `pin: true`**를 붙인다.
  메모를 합치거나 줄일 때도 이런 정보가 제목에서 빠지지 않았는지 확인한다.
- 지하철 출구나 역 이름 메모에는 `"onlyMode": "transit"`, 주차 메모에는 `"onlyMode": "car"`를 붙인다.
- 자료끼리 엇갈리면 `trust`에 "확인 필요"를 붙이고, 확인하지 못한 정보는 지어내지 않고 뺀다.

### 메모 한 개의 항목

| 항목 | 뜻 |
|---|---|
| `title`, `body` | 제목, 내용 |
| `category` | 분류 (가는 길, 주차, 아이와 함께 …) |
| `conditions` | 관련 조건: `lost`(길치), `kid`(아이), `car`(자차), `transit`(대중교통). 2026-11-01부터 길치·대중교통은 항상 켜진 기준, 사용자가 고르는 것은 `kid`뿐 |
| `onlyMode` | 이 이동수단일 때만 보이는 카드 (`car` 또는 `transit`, 없으면 항상 보임) |
| `importance` | 기본 중요도 (숫자가 클수록 위로) |
| `pin` | `true`면 스위치와 상관없이 "꼭 기억할 3가지" 맨 앞에 고정 (출입 필수 정보 등, 장소당 2개까지) |
| `trust` | 신뢰도 표시 (예: "확인 필요", "후기 엇갈림") |
| `warn` | `true`면 빨간 주의 카드 |
| `source` | 출처 |
| `photos` | 사진 목록 (직접 찍었거나 사용 허락받은 것만) |

## 개발 기록

### 왜 이 문제를 골랐나
처음 가는 곳에 갈 때 정보는 지도 앱, 블로그, 커뮤니티에 흩어져 있다. 그리고 "길을 잘 잃는 사람"과
"아이와 함께 가는 사람"이 궁금한 건 서로 다르다. 같은 메모라도 **내 상황에 따라 순서만 바꿔줘도**
이동 중에 훨씬 빨리 찾을 수 있겠다는 생각에서 시작했다. 처음에는 HTML 한 장짜리 시험판으로
"스위치를 켜면 카드 순서가 바뀐다"는 아이디어가 쓸모 있는지부터 확인했다.

### 기술 선택: 순수 HTML + JavaScript
| 후보 | 결과 | 이유 |
|---|---|---|
| **순수 HTML+JS** | ✅ 선택 | 설치할 것이 없고 시험판과 구조가 같아 이해하기 쉽다. Vercel에 무료로 바로 올릴 수 있다. |
| React + Vite | 탈락 | 화면을 부품 단위로 나누기 좋지만, 설치·빌드 단계가 생긴다. 지금 화면 크기에서는 얻는 게 적다. |
| Next.js | 탈락 | 서버 기능까지 있지만 지금 규모에 비해 배울 것이 너무 많다. |

날씨 API처럼 인증키를 숨겨야 하는 기능은 Vercel 서버리스 함수(인증키를 숨겨 주는 작은 서버 코드)
파일 하나만 더해서 해결할 계획이다.

### 시험판 → 데이터 분리하면서 막혔던 점
시험판은 "어떤 카드를 숨길지"를 정할 때 `if (n.id === "sign" ...)`처럼 **특정 카드 이름을 코드에 직접**
적어 두고 있었다. 장소가 하나일 땐 괜찮지만 장소가 늘어나면 장소마다 코드를 고쳐야 한다.
→ 메모 데이터에 `onlyMode`(이 이동수단일 때만 보이기) 항목을 새로 만들어 규칙을 **데이터로** 옮겼다.

이렇게 바꾸고 시험판과 스위치 조합 8가지를 자동으로 비교했더니, 6가지는 결과가 똑같았다.
다른 2가지(자차 + 길치)에서 **시험판이 차로 가는 사람에게 "이촌역 2번 출구로 나오세요" 카드를 맨 위에
띄우고 있었다**는 걸 발견했다. 예외 코드가 겹치면서 생긴 버그로 보고, 새 규칙에서는 숨기기로 했다.

### 장소가 수백 개가 될 것을 생각한 설계
- **장소 하나 = 폴더 하나**: 사진까지 한 폴더에 묶어야 옮기거나 지울 때 실수가 없다.
- **목록 자동 생성**: 웹페이지는 서버 폴더 안 파일 목록을 직접 읽을 수 없다. 목록을 손으로 고치면
  수백 개일 때 빠뜨리기 쉬워서, `npm run build`가 폴더를 훑어 목록을 만들게 했다.
- **형식 검사**: 장소가 많아지면 오타가 생긴다. 필수 항목 누락, 조건 이름 오타(`kids` 등),
  사진 출처 누락, 없는 사진 파일을 한국어로 알려준다.
- **목록은 가볍게**: 첫 화면 목록에는 이름·주소만 담고, 메모는 장소를 고를 때만 불러온다.

### 검사기를 시험하다 발견한 버그
일부러 망가뜨린 장소 파일로 검사기를 시험했는데, 엉뚱하게도 "파일을 읽을 수 없어요"만 나왔다.
원인은 윈도우에서 저장할 때 파일 맨 앞에 붙는 **눈에 안 보이는 글자(BOM)**였다. 메모장으로
장소 파일을 고치면 똑같은 일이 생길 수 있어서, 검사기가 이 글자를 떼고 읽도록 고쳤다.
고친 뒤에는 넣어 둔 실수 5개를 모두 찾아냈다.

### 시험판보다 바꾼 화면
- 스위치를 **화면 위에 고정**했다. 시험판에서는 메모를 보다가 상황을 바꾸려면 맨 위로 다시 올라가야 했다.
- 점수가 높은 카드 4개만 펼치고, 나머지는 **제목만 보이게 접었다**. 이동 중에 훑어보기 쉽게 하려는 것이다.
- 스위치 상태를 주소와 브라우저에 기억해서 새로고침해도 유지되고, 링크로 공유할 수 있다.
- 헷갈리는 갈림길이나 안내판을 보여줄 **사진 자리**를 만들었다. 사진은 저작권 문제를 피하려고 직접 찍었거나
  사용 허락을 받은 것만 쓰고, 출처(`credit`)가 없으면 검사기가 막는다.

### 2단계: 두 번째 장소(서울숲)를 넣으며 배운 것
- **데이터 구조가 버티는지 시험**: 코드는 한 줄도 고치지 않고 `places/seoul-forest/` 폴더만 추가했다.
  장소가 2곳이 되자 첫 화면이 자동으로 "장소 고르기"로 바뀌었다. 장소 전용 코드를 없앤 설계가 의도대로 동작했다.
- **사실 확인 방법**: 서울시 기사(내 손안에 서울), 서울숲 누리집 묻고 답하기, 육아 정보 사이트를 읽고
  자료끼리 맞춰 봤다. 출구 번호는 3번(2020년 기사)과 4번(2024년 기사)으로 엇갈렸는데, 둘 다 공원으로
  이어진다는 자료가 있어서 "3·4번"으로 적었다. 주차 요금(150원과 200원)과 곤충식물원 시간처럼 끝까지
  엇갈리는 정보에는 '확인 필요'를 붙였다. 화장실 위치는 믿을 만한 자료를 못 찾아서 **넣지 않았다**.
- **메모별 출처를 채움**: 1단계 시험판 메모는 출처가 비어 있었다. 서울숲부터는 메모마다 `source`를 적었다.
- **발견한 버그 1: 브라우저가 예전 장소 목록을 씀**. 장소를 추가했는데 첫 화면에 여전히 용산가족공원만 떴다.
  브라우저가 전에 받은 목록 파일(1곳짜리)을 저장해 두고 재사용한 것이다(캐시). 장소를 계속 추가할 앱이라
  치명적이어서, 장소 파일을 부를 때 "바뀌었는지 매번 확인"하도록 고쳤다.
- **발견한 버그 2: 자차인데 지하철 안내가 요약에 나옴**. 요약 문장의 조건(`when`)은 한 가지만 볼 수 있다.
  그런데 "뚝섬역과 뚝섬유원지역은 달라요"를 '길치' 문장에 넣었더니 자차 + 길치에서도 나왔다. 지하철 이야기는
  '대중교통' 문장으로 옮겨서 해결했다. → 장소를 쓸 때의 규칙: **요약 문장 하나에는 조건 하나에 해당하는 내용만**.

### 3단계: 날씨 연결 (기상청 초단기예보)
- **왜 서버 코드가 필요했나**: 인증키를 화면 코드(app.js)에 넣으면 누구나 브라우저에서 키를 볼 수 있다.
  그래서 키는 서버에만 두고, 화면은 `api/weather`에 "이 좌표 날씨 알려줘"라고만 묻게 했다.
- **실행 방법을 바꾼 이유**: Python 서버는 화면 파일만 보여줄 수 있고 서버 코드는 못 돌린다. 후보는 두 가지였다.
  | 후보 | 결과 | 이유 |
  |---|---|---|
  | Vercel 공식 도구(`vercel dev`) | 탈락 | 배포 환경과 가장 비슷하지만, 지금 바로 Vercel 가입·로그인·도구 설치가 필요하다. |
  | **Node.js로 만든 작은 서버** | ✅ 선택 | 추가 설치가 없다. 날씨 코드는 Vercel 형식으로 써서 배포할 때 그대로 올라간다. |
- **어떤 예보를 쓸까**: 기상청 API에는 초단기실황(지금), 초단기예보(6시간), 단기예보(3일)가 있다. 앱 콘셉트가
  "30분 먼저 다녀온 메모"라서 **이동하는 동안과 도착 후 몇 시간**이 중요하다고 보고, 한 번의 호출로
  기온·하늘·비 소식을 6시간치 받을 수 있는 초단기예보를 골랐다.
- **좌표 → 격자**: 기상청은 위도·경도가 아니라 5km 격자 번호로 날씨를 준다. 장소 파일에 `lat`, `lon`을 넣고
  기상청 공개 변환식으로 바꿨다. 서울시청 좌표로 시험해 기상청 공식 격자(60, 127)와 맞는지 확인했다.
- **발표 시각 계산에서 신경 쓴 점**: 초단기예보는 매시 30분에 만들어져 45분쯤부터 받을 수 있다. 그래서 45분 전에는
  한 시간 전 발표분을 쓴다. 자정 직후(00:20)에는 **날짜도 하루 전으로** 넘어가야 해서 그 경우도 따로 시험했다.
- **키 없이 시험하기**: 키 발급을 기다리는 동안 기상청 응답을 흉내 낸 가짜 데이터로 시험했다.
  정상 응답, 그리고 "키 등록 대기"(기상청이 JSON 대신 XML 오류를 보내는 경우)를 모두 확인했다.
- **발견한 버그: 고친 화면이 안 보임**. 서버를 바꾸고 나서도 브라우저가 예전 index.html을 계속 보여줬다(2단계와 같은
  캐시 문제). 내 컴퓨터용 서버가 "매번 바뀌었는지 확인하라"는 표시를 붙여 보내도록 고쳤다.
- **호출 횟수 아끼기**: 공공데이터 API는 하루 호출 한도가 있어서, 같은 날씨는 배포 서버에서 10분간 재사용하게 했다.
- **신청할 때 헷갈렸던 점**: "기상청 단기예보"를 검색하면 기상청 API허브 사이트와 "API허브 연계" 버전이 함께 나온다.
  둘은 주소와 키 형식이 달라서, 공공데이터포털의 **"기상청_단기예보 조회서비스"(API허브라는 말이 없는 것)**를 골랐다.
  지금 포털은 Encoding/Decoding 구분 없이 "일반 인증키" 하나만 보여준다. 신청하자마자 자동 승인됐고 키도 바로 작동했다.
- **날씨를 메모와 연결**: 처음엔 3시간 안에 비나 눈 예보가 있으면 요약 맨 앞에 "○시쯤 비 예보가 있어요. 우산을 챙기세요."를
  붙였다. (이후 실사용 피드백으로 날씨를 화면 위로 올리면서, 비 소식은 날씨 줄에서 강조하는 것으로 바꿨다.)

### 4단계: 방문자 한 줄 제보
- **왜 필요한가**: 메모와 날씨는 "미리 알 수 있는 정보"다. 그런데 "지금 입구 줄이 긴지", "주차장이 찼는지"는
  그 자리에 있는 사람만 안다. 이 빈칸을 방문자가 한 줄로 채우게 했다.
- **저장 위치**: 우선 브라우저 저장소(localStorage, 내 브라우저 안에만 남는 저장 공간)에 장소별로 저장한다.
  다른 사람에게는 아직 보이지 않는다는 점을 화면에 그대로 적었다. 기능이 있는 척하지 않으려는 것이다.
  저장·불러오기 함수(`loadReports`, `saveReports`) 두 개만 고치면 나중에 서버 저장으로 옮길 수 있게 묶어 뒀다.
- **시간 규칙**: 현장 정보는 금방 낡는다. 3시간이 지나면 "오래됨"으로 흐리게 보여주고 "지금 붐비나요" 숫자에서 빼며,
  24시간이 지나면 지운다. 미리 4시간 전·25시간 전 제보를 심어 놓고 각각 흐려지고 지워지는지 시험했다.
- **빠른 문장 버튼을 바꾼 이유**: 처음엔 "입구 줄 길어요" 버튼을 누르면 바로 등록되게 했다. 그런데 이동 중에 손가락이
  잘못 닿으면 거짓 제보가 생긴다. 그래서 버튼은 입력칸만 채우고, 확인하거나 "(20분쯤)"처럼 덧붙인 뒤 등록하게 바꿨다.
- **안전**: 제보에 `<img onerror=...>` 같은 코드 글자를 넣어도 글자로만 보이고 실행되지 않는지 시험했다
  (나중에 다른 사람 제보가 보이게 되면 중요해지는 부분). 빈칸 등록은 막았고, 글자 수는 40자로 제한했다.

### 5단계: 제보를 다른 방문자와 공유 (Upstash Redis)
- **저장소 선택**: 후보는 두 가지였다.
  | 후보 | 결과 | 이유 |
  |---|---|---|
  | **Upstash Redis** | ✅ 선택 | Vercel 화면에서 바로 연결된다. "24시간 뒤 자동 삭제"처럼 짧게 사는 데이터에 맞고, 웹 주소(REST)로 주고받아 추가 설치가 없다. |
  | Supabase | 탈락 | 표 형태의 본격 데이터베이스라 확장성은 좋지만, 가입·표 설계·보안 규칙 설정 등 지금 필요 이상으로 단계가 많다. |
- **막혔던 곳: 무료 요금제가 안 보임**. 새 저장소를 만들려는데 유료 요금제만 나왔다. 다른 프로젝트(daily-ai)가 이미 무료
  저장소를 쓰고 있었기 때문이다. 유료로 가는 대신 **같은 저장소를 함께 쓰고**, 이 앱의 데이터 이름은 모두 `fvg:`로
  시작하게 해서 섞이지 않게 했다. 제보는 24시간 뒤 사라져서 용량 부담도 거의 없다.
- **아무나 쓰는 게시판의 안전장치**
  - 도배 방지: 같은 사람은 1분에 한 번. 이를 위해 접속 주소(IP)를 쓰지만 **원래 모습 그대로 저장하지 않고** 알아볼 수 없게
    바꾼 값(해시)으로 1분만 기억한다.
  - 링크가 들어간 글, 40자 초과, 없는 장소에 대한 제보는 서버에서 거절한다. 화면에서 막는 것만으로는 우회할 수 있어서다.
  - 내가 쓴 제보만 지울 수 있다. 등록할 때 내 휴대폰에 비밀 값을 남기고, 서버에는 그 값의 지문(해시)만 저장한다.
  - "전화번호 같은 개인정보는 쓰지 마세요" 안내를 입력칸 아래에 둔다.
- **망가지지 않게**: 저장소가 연결 전이거나 서버가 응답하지 않으면 자동으로 예전 방식(내 브라우저에만 저장)으로 바뀐다.
  그래서 저장소 연결 전에 코드를 먼저 배포해도 사이트가 멀쩡했다.
- **시험**: 진짜 저장소를 연결하기 전에 Upstash를 흉내 낸 가짜 저장소로 등록·도배 방지·남의 제보 지우기 차단·24시간 정리를
  확인했다. 연결 후에는 실제 사이트에서 제보를 올리고, 내 기기 기억을 지운 "다른 기기" 상태에서도 제보가 보이는지,
  그 상태에선 "지우기" 버튼이 안 보이는지 확인한 뒤 시험 제보를 지웠다.

### 실사용: 내가 처음 가는 곳에 직접 써보다 (2026-10-28, 일산 MBC 드림센터)
다음 날 오전에 처음 가야 하는 곳이 생겨서 전날 밤 장소를 추가하고, 당일 대중교통으로 가면서 실제로 썼다.
- **메모가 비어 있던 곳을 현장 제보가 채웠다**: 공식 안내에는 출입 절차가 없어서 "업무 방문 절차 확인 필요"로
  남겨 뒀던 부분이 있었다. 현장에서 "1층에서 출입증 받을 때 **담당자 이름과 연락처가 필요해요**"라고 제보를 남겼다.
  제보는 24시간 뒤 사라지므로, 이 내용을 메모로 옮기고 출처를 "직접 방문"으로 적었다. 확인이 끝나서 '확인 필요' 표시도 뗐다.
  → 메모(미리 조사한 것)와 제보(현장에서 확인한 것)가 서로 보완하는 흐름이 실제로 한 번 돌았다.
- **날씨 위치 피드백**: "날씨(기온, 비 소식)는 위에 있어야 좋겠다." 처음엔 화면 아래 "지금 상황" 칸에 도로·제보와 나란히
  두었는데, 이동 중에 가장 먼저 보고 싶은 정보였다. 장소 이름 바로 아래 한 줄로 올리고, 비 소식이 있으면 노랗게 강조했다.
- **글꼴 피드백**: "사용자가 편하게 느끼는 글꼴이 좋겠다(나는 나눔고딕이 좋은데 사용성이 좋은지 모르겠다)."
  시험판 분위기를 이어받아 장소 이름·요약 한 줄에 명조 계열(고운바탕)을 쓰고 있었는데, 이동 중 흔들리는 화면에서
  가장 중요한 요약이 명조인 건 불리하다고 판단했다. 나눔고딕도 검토했지만 굵기가 3가지뿐이고, 이 앱은 "1번 출구",
  "150m", "13°"처럼 숫자가 중요해서 화면용으로 만들어진 **프리텐다드**로 전부 통일하고 강약은 굵기로 줬다.
- **중복 피드백**: "중복된 텍스트를 정리할 필요가 있다." 살펴보니 노란 요약 문장이 바로 아래 카드 내용을 거의 그대로
  반복하고 있었다(예: 요약의 "정발산역 1번 출구로 나와 150m…" = 첫 카드 본문). 원인은 구조였다. 장소마다 요약 문장(`summary`)과
  메모를 **따로 손으로 써서**, 같은 사실이 두 번 들어갈 수밖에 없었다. 검토한 방법은 세 가지였다.
  | 방법 | 결과 | 이유 |
  |---|---|---|
  | **요약을 "꼭 기억할 3가지" 목록으로 자동 생성** | ✅ 선택 | 가장 중요한 메모 3개의 제목만 보여주고 누르면 펼친다. 그 3개는 아래 목록에서 빼서 한 번만 나온다. 요약을 따로 쓰지 않으니 장소 추가 작업도 줄고, 메모를 고치면 요약도 저절로 맞는다. |
  | 요약은 두고 겹치는 카드를 접기 | 탈락 | 화면 중복은 줄지만 장소마다 요약과 메모를 따로 써야 하는 수고와 둘이 어긋날 위험이 남는다. |
  | 요약 칸 없애기 | 탈락 | 가장 단순하지만 "한눈에 핵심"을 보는 칸이 사라진다. |
  비 소식도 날씨 줄과 요약에 두 번 나오고 있어서, 요약에서는 빼고 날씨 줄 강조만 남겼다. 카드끼리 겹치던 문장
  (예: "호수공원 앞"이 세 카드에, "일산동구청"이 두 카드에 등장)도 한 카드에만 남기도록 정리했다.
- **정리하다 필수 정보를 지워 버린 실수**: 중복을 줄이면서 "신분증" 카드를 현장 제보로 만든 "담당자 연락처" 카드에
  합쳤는데, 제목은 담당자 쪽만 남기고 신분증은 본문 속 "방청이라면…" 한 문장으로 줄였다. 바로 지적이 왔다.
  "신분증을 이 웹에서 못 봤으면 여기까지 와서 **출입도 못 할 뻔했다**." 업무 방문에도 신분증이 필요하다는 점과,
  이 정보가 제목에서 사라져 눈에 띄지 않게 된 점이 문제였다.
  - 원인: 중복 정리를 "같은 말 줄이기"로만 봤고, 정보의 **무게**(없으면 목적 자체를 못 이루는 정보인가)를 따지지 않았다.
    또 "꼭 기억할 3가지"가 스위치 점수로만 정해져서, 길치를 켜면 출입 카드가 길 찾기 카드에 밀려 아래로 내려갔다.
  - 고친 것: 출입에 필요한 두 가지를 제목에 모두 넣었다("신분증 + 만날 담당자 연락처가 있어야 들어가요").
    그리고 메모에 **`pin`(항상 맨 위)** 표시를 새로 만들어, 스위치와 상관없이 "꼭 기억할 3가지"의 1번에 고정했다.
    고정 메모가 많아지면 3가지의 의미가 흐려지므로 장소당 2개까지만 허용하고, 검사기가 막는다.
  - 교훈: 사용자가 "처음 가는 곳"에서 가장 피해야 할 일은 헤매는 것보다 **도착하고도 못 들어가는 것**이다.
- **함께 고친 것**: 날씨를 확인하다가, 서버를 막 켰을 때나 기상청이 잠깐 오류를 낼 때 날씨 칸이 실패로 끝나는 것을 봤다.
  현장에서 휴대폰으로 볼 때도 생길 수 있는 일이라, 연결 문제일 때는 1.5초 뒤 한 번 더 물어보게 했다.

### 장소를 늘리기 전에 "품질 기준"부터 (2026-10-29)
- **순서 판단**: "장소를 무수히 추가하기"와 "지금 장소의 품질 높이기" 중 무엇을 먼저 할지 고민했다. 이틀 동안 장소 파일 형식이
  세 번 바뀌었다(좌표 추가, 요약 삭제, `pin` 추가). 장소가 3곳일 땐 금방 고쳤지만 100곳이었다면 모두 다시 손봐야 했다.
  그래서 **품질 기준을 먼저 정하되 짧게 끝내고**, 그 기준으로 장소를 늘리기로 했다.
- **기준은 실제로 겪은 일에서 나왔다**: 신분증을 놓칠 뻔한 일 → 체크리스트 1번 "출입 조건", 화장실 위치를 못 찾았지만 지어내지
  않은 일 → "확인 못함"도 기록, 요약과 카드 중복 → "한 사실은 한 카드에".
- **"붐비는 때" 항목 추가**: 사용자 아이디어("예전 티맵에서 그 장소를 지금 목적지로 정한 사람 수가 보였다, 어린이날
  서울대공원 같은 때 참고가 된다"). 티맵의 그 데이터는 외부에 공개돼 있지 않았다. 대신 한국관광공사의 "관광지 집중률 예측"
  (통신사 이동 데이터 기반, 앞으로 30일, 상대 점수)을 찾았다. 관광지 목록에 있는 곳만 되는 한계가 있어서, 체크리스트에 8번
  "붐비는 때"를 넣어 데이터가 없는 장소도 조사 메모로 대비하게 했다. 데이터 연결은 다음 단계에서 한다.
- **검사기로 강제**: 체크리스트 결과를 장소 파일의 `checked`에 남기게 하고, 8가지 중 하나라도 빠지거나 없는 메모를 가리키면
  `npm run build`가 막는다. "확인 못함"을 따로 둔 이유는 **빠뜨린 것**과 **찾아봤지만 없는 것**을 구분하기 위해서다.
- **기존 3곳 점검 결과**: 일산 MBC의 "붐비는 때"는 자료를 못 찾아 "확인 못함"으로 남겼다. 서울숲의 2년 넘은 자료(2020년 기사,
  2022년 이전 누리집) 메모 2개에 "확인 필요"를 붙였다.

- **기준으로 넣은 첫 장소: 광화문광장**. 체크리스트 8가지를 모두 채웠다. 특히 "붐비는 때"에서 2026년 집회·응원·공연 때
  광장과 세종대로가 통제된 사례를 찾아 빨간 주의 카드로 넣었다. 조사하면서 규칙 하나를 더 배웠다. 주차 카드 제목에
  블로그 출처 요금("5분당 430원")을 넣었더니, 접힌 카드에서는 '요금 확인 필요' 표시가 안 보여 확실한 정보처럼 보였다.
  → **확인 안 된 숫자는 제목에 넣지 않는다**를 기준 문서에 추가했다.

### 만들었다가 뺀 기능: 주변 도로 상황
- **만든 과정**: "지금 상황" 칸에 도로 정보를 넣으려고 서울 TOPIS를 먼저 생각했다. 그런데 일산 MBC(경기도)가 들어오면서
  전국 데이터가 필요해졌고, 국가교통정보센터(ITS)의 실시간 도로 속도로 바꿨다. 장소 좌표 주변 약 2km 도로의 속도로
  원활·서행·정체를 판단하고, 자차일 때 정체면 안내를 띄우는 서버 코드를 만들어 가짜 데이터로 시험까지 마쳤다.
- **막힌 곳**: 인증키를 받으려는데 교통정보센터 사이트가 "서버 내부 에러"를 냈다. 공공데이터포털에서 대신할 데이터를
  찾아봤지만 고속도로만 있거나, 정해진 서버 주소에서만 호출을 허용하는 등(Vercel과 맞지 않음) 마땅한 게 없었다.
  나중에 신청 화면에 들어가 보니 개발용 한도가 **한 달 100건**이라 그대로는 쓰기 어려웠다.
- **뺀 이유 (사용자 판단)**: "이 앱을 쓰는 사람에게 더 유용한 건 도로 속도보다 **붐비는지 여부**다. 너무 붐비면 오늘
  그 목적지에 가지 않는 선택을 할 수 있다." 맞는 말이었다. 길 찾기와 실시간 도로 상황은 지도 앱이 이미 잘한다.
  이 앱만 줄 수 있는 가치는 "가기 전에 판단할 거리"다. 그래서 도로 기능은 빼고(코드는 깃 기록에 남김), 같은 자리를
  "오늘 붐빔 예측"으로 바꿨다.
- **배운 점**: 기능을 만들 수 있다는 것과 사용자에게 필요하다는 것은 다르다. 다 만든 기능이라도 앱의 목적("처음 가는 곳에
  가기 전에 판단하고 준비하게 돕기")에서 멀면 덜어낸다.

### 오늘 붐빔 예측 (한국관광공사 관광지 집중률)
- **왜**: "너무 붐비면 오늘 그 목적지에 가지 않는 선택을 할 수 있다"는 사용자 판단에서 출발했다(도로 기능을 뺀 이유와 같다).
- **데이터**: 한국관광공사 "관광지 집중률 방문자 추이 예측"(통신사 이동 데이터 기반, 관광지별 앞으로 30일). 공공데이터포털
  인증키는 계정당 하나라서 날씨 키를 그대로 썼다(새 키를 붙여넣을 필요가 없었다). 문서에 기능 이름이 빠져 있어 실제 호출로
  주소를 확인했고, 장소 4곳 중 관광지 3곳이 목록에 있었다(일산 MBC는 없음 → 줄을 숨긴다).
- **숫자를 그대로 보여주지 않은 이유**: 점수는 "그 장소가 가장 붐빌 때 = 100"인 상대 점수라 70점이 한산한지 붐비는지 감이 오지
  않는다. 실제로 값이 대부분 50~100 사이에 몰려 있어서, 다른 프로젝트처럼 "75 이상 = 붐빔"으로 자르면 거의 매일이 붐빔이 된다.
  그래서 **그 장소의 앞으로 30일과 비교**해 오늘이 상위 20%면 "붐빔 예상", 하위 30%면 "한산할 듯", 그 사이면 "보통"으로 보여준다.
- **대안 제시**: "오늘 가지 말까?"를 판단할 때 바로 다음 행동이 보이도록, 일주일 안에서 오늘보다 덜 붐비는 날 2개를
  "덜 붐비는 날: 11/2(월) · 11/3(화)"처럼 알려준다. 중요한 판단 정보라 날씨 줄 바로 아래에 두고, 붐빔이면 빨갛게 강조한다.
- **함께 잡은 실수**: 계산 함수에 모듈 전용 문법(`export`)을 붙였는데, 이 화면 코드는 일반 스크립트라 그대로 두면 화면 전체가
  멈췄을 것이다. 배포 전에 문법 검사(`node --check`)로 확인하는 단계를 넣었다.

### 장소 5곳 추가 (2026-10-30): 고르는 기준부터 정하기
- **고른 기준**: ① 이 앱 사용자에게 "처음 가면 어려운 곳"(길치가 헤매는 곳, 아이 동반에 예약·시설 정보가 중요한 곳,
  휴관일·예약제처럼 **도착하고도 못 들어가는 함정**이 있는 곳) ② 붐빔 예측·공식 사진·공식 운영 정보가 있어 앱 기능이 제대로
  동작하는 곳 ③ 실내/야외, 서울/경기를 섞기. → 서울대공원(어린이날 붐빔, 넓음), 국립중앙박물관(어린이박물관 예약제),
  코엑스 별마당도서관(지하 미로), 경복궁(화요일 휴궁), 서울식물원(월요일 온실 휴관).
- **넣기 전에 데이터부터 확인**: 5곳 모두 붐빔 예측과 사진이 있는지 먼저 조회했다. 처음엔 전부 "없음"이 나왔는데, 관광공사
  서버의 **연결 시간 초과**였다(데이터가 없는 게 아니라 요청이 실패한 것). 재시도를 넣어 다시 확인했다. 코엑스는 붐빔 예측에
  "한국종합무역센터(코엑스)"라는 이름으로 있어서, 구 전체 목록을 훑어 찾았다.
- **운영 정보는 관광공사 API에서**: 이용시간·휴무일·주차 요금을 관광공사 관광정보 API로 한 번에 받아 출처를 통일했다.
  못 찾은 항목(예: 서울식물원 수유실)은 지어내지 않고 체크리스트에 "확인 못함"으로 남겼다.
- **발견한 버그: 쉬는 날을 "덜 붐비는 날"로 추천**. 경복궁 화면에 "덜 붐비는 날: 11/3(화)"가 떴는데 화요일은 휴궁이다.
  문 닫는 날은 사람이 없으니 예측 점수가 낮게 나오는 게 당연했다. 그대로 두면 앱이 "도착하고도 못 들어가는" 상황을 만든다.
  → 장소 파일에 `closedWeekdays`(쉬는 요일)를 넣고, 붐빔 비교와 추천에서 그 요일을 빼게 했다. 오늘이 쉬는 날이면
  "오늘은 쉬는 날이에요"를 빨갛게 먼저 보여준다. 데이터를 그대로 믿지 않고 **다른 정보(휴무일)와 맞춰 보는 것**의 중요성을 배웠다.
- **사진**: 관광공사 1유형 사진이 있는 3곳은 미리보기로 같이 골랐고(서울대공원 스카이리프트, 국립중앙박물관 석탑 복도,
  경복궁과 북악산), 없는 2곳은 위키미디아에서 골랐다(별마당도서관 퍼블릭 도메인, 서울식물원 온실 CC BY-SA). 코엑스 사진은
  아래쪽에 사람이 많아 책장 위주로 보이게 위치를 맞췄다.

    잔디밭 사진을 골라 배너를 **사진 맨 아래에 맞췄다**(`position: center 100%`). 한강까지 함께 보이는 사진은 찾지 못해 다음 과제로 남겼다.
  - 창덕궁: 작은 미리보기만 보고 "인정전"이라고 소개했는데, 받아 보니 **정문 돈화문**이었다. 사용자에게 바로 정정했고, 돈화문은
    처음 가는 사람이 실제로 들어가는 문이라 그대로 썼다. → 사진을 소개할 때는 **크게 확인한 뒤** 설명한다.
- **화면 확인 중 착각**: 북촌·창덕궁의 붐빔 예측 줄이 안 보여서 버그인 줄 알았는데, 관광공사 서버가 첫 요청에 늦게 답한 것이었다.
  확인 시간을 늘리니 정상으로 떴다. 앱은 한 번 더 물어보는 기능이 있어서 실제 사용자는 조금 늦게 보게 될 뿐이다.

### 첫 화면 다시 만들기: 카테고리별 사진 카드 (2026-10-30)
- **문제**: 장소가 19곳이 되자 이름·주소만 나열된 첫 화면이 길어졌다.
- **검토한 방법** (사용자 아이디어 두 가지와 비교)
  | 방법 | 결과 | 이유 |
  |---|---|---|
  | 지도 + 핀 | 나중에 | "내 주변" 찾기엔 좋지만, 서울 도심 장소가 몰려 있어(경복궁·광화문·창덕궁·북촌) 휴대폰에선 핀이 겹친다. 이 앱을 여는 사람은 갈 곳을 이미 정한 경우가 많고, 지도 서비스 키도 새로 필요하다. |
  | **카테고리별 사진 카드 + 좌우 넘기기** | ✅ 선택 | 새로 넣은 대표 사진이 살아나고, 장소가 늘어도 카테고리마다 한 줄이라 화면이 길어지지 않는다. 지금 기술 그대로 만들 수 있다. |
- **이 앱다운 한 가지**: 카드 사진 위에 "월 휴무"(쉬는 요일에서 자동), "후원 예약 필요"·"17시~10시 출입 금지"(`notice`) 같은
  표시를 붙였다. "도착하고도 못 들어가는" 정보를 **장소를 고르는 순간부터** 보여주기 위해서다.
  - 사용자 피드백: "어린이박물관 예약"은 누르면 예약이 될 것 같은 버튼처럼 읽힌다 → "어린이박물관 예약 필요"로.
    표시는 **상태를 알리는 말**("~필요", "~휴무", "~금지")로 끝내야 버튼과 헷갈리지 않는다.
- **검색은 그대로**: 이름을 아는 사람을 위해 맨 위 검색창을 남기고, 검색어를 입력하면 맞는 장소만 사진 카드로 보여준다.
- **데이터로 관리**: 카테고리 목록은 `places/categories.json`, 장소의 소속은 `place.json`의 `categories`에 둔다. 한 장소가 여러
  카테고리에 들어갈 수 있다(예: 롯데월드 = 아이와 함께·실내·테마파크). 검사기가 없는 카테고리나 긴 안내 문구를 막는다.
- **고친 것**: 좌우로 넘길 때 첫 카드가 화면 왼쪽 끝에 붙어 이름이 잘렸다. 넘기기가 멈추는 위치가 화면 가장자리 기준이었기 때문이라,
  본문 여백(16px) 안쪽에서 멈추게 했다.
- **사용자 제보로 고친 것 (밝은 화면)**: "이것봐 무슨 글씨인지 하나도 안보여" — 사진 위 빨간 표시의 글씨가 안 보였다.
  표시 글씨는 흰색으로 정했는데, 카드 아래 지역 이름에 쓰던 회색 규칙(`.pcard span`)이 더 강하게 적용돼 표시 글씨까지 회색이 됐다.
  나는 어두운 화면에서만 확인해서(밝은 회색이라 그럭저럭 읽힘) 놓쳤다. 지역 이름 규칙을 카드 바로 아래 글자(`.pcard > span`)로
  좁히고, 표시는 더 진한 빨강 + 그림자로 바꿨다. **이후 화면을 바꾸면 밝은·어두운 화면 둘 다 확인**하기로 했다.
- **사용자 제보: "누르면 더 나온다는 걸 모르겠다"**: 메모 카드 오른쪽의 작은 "▾"는 분류 글자(예: "주차") 옆에 붙어 있어
  글자의 일부처럼 보였다. 오른쪽 끝에 **동그란 화살표 버튼**을 따로 두고, 펼치면 화살표가 위로 돌아가게 했다.
- **첫 화면 제목 바꾸기**: "어디로 가세요?"는 아무 앱에나 쓸 수 있는 말이라 이 앱이 주는 것(붐빔·쉬는 날·헷갈리는 길)을 설명하지 못했다.
  1차로 사용자 가족이 쓰는 말 "오늘 눈치게임 성공했다"에서 **"오늘 눈치게임, 성공해볼까요?"**를 골랐는데, 사용자가 다른 AI에
  "눈치게임" 하면 떠오르는 것을 물어보니 숫자 외치기 놀이·심리전·조직 내 눈치 보기가 나왔다. **우리 가족에겐 익숙해도 다른 사람에겐
  이 뜻으로 통하지 않는 말**이라 뺐다. 최종은 사용자가 처음 낸 후보 **"지금 여기 가도 될까요?"** — 붐빔만 떠올리게 한다는 약점은
  아래 설명 줄로 채웠다. 설명 줄도 사용자가 다시 짚었다: "처음 가는 곳을 고르면"은 기능 설명일 뿐, 기획 의도
  — ① 오늘 가도 되는지(붐빔) ② 기껏 갔는데 휴무인 헛걸음 피하기 ③ 길 헤맬 가능성 줄이기 — 가 안 보인다. 그래서 세 가지를
  그대로 담아 "처음 가는 곳, 오늘 붐비는지·쉬는 날은 아닌지, 어디서 길을 헤매기 쉬운지 미리 알려드려요."로 바꿨다. 배운 것: 문구는 만든 사람의 감각이 아니라 처음 보는 사람 기준으로 확인한다.
- **일산 MBC 드림센터 삭제**: 사용자 판단 "업무로 가는 사람 말고는 검색할 일이 없다." 장소 목록에서는 뺐지만, 실사용 기록
  (출입증·신분증 이야기)은 이 README에 그대로 남겼다.

### 영어·중국어·일본어 (2026-10-30): "처음 가는 사람"을 넓혀 보기
- **계기 (사용자 아이디어)**: "관광 목적으로 한국에 온 외국인에게는 모든 곳이 처음일 것 같아." 이 앱의 대상(처음 가는 사람)을
  가장 넓게 해석하면 외국인 관광객이다. 영어·중국어·일본어로 보여주고, **외국인에게만 필요한 정보는 없을까**도 함께 고민했다.
- **번역 방법 — 검토한 세 가지**
  | 방법 | 결과 | 이유 |
  |---|---|---|
  | 브라우저 자동 번역에 맡기기 | 탈락 | 할 일은 없지만 "해치마당"이 "Haechi Yard"가 되는 식으로 고유명사가 엉뚱해진다. 길 안내 앱에선 치명적. |
  | 번역 서비스(파파고·구글)를 실시간 연결 | 탈락 | 인증키·비용이 생기고 고유명사 문제는 그대로. |
  | **장소를 추가할 때 미리 번역해 파일로 저장** | ✅ 선택 | 비용 0원, 인증키 없음. 장소·역 이름을 한국관광공사 외국어 관광정보의 공식 표기로 맞출 수 있다. 화면에 "AI 번역"이라고 밝힌다. |
- **번역에서 정한 원칙**: 지도 앱 검색어·역 이름처럼 **현장에서 한국어로 보게 되는 말은 괄호에 한국어를 같이** 쓴다
  (`Gwanghwamun Station (광화문역)`). 외국인이 들고 다니며 대조해야 하는 건 번역이 아니라 표지판의 한국어이기 때문이다.
- **외국인에게 필요한 다른 정보** — 같은 장소라도 막히는 곳이 다르다.
  - 구글 지도는 한국에서 걷기·운전 길 안내가 안 된다(2026년 8월에도 미출시) → 네이버 지도 링크 (처음엔 카카오맵도 넣었다가 아래 이유로 뺌)
  - 택시 기사에게 보여줄 **한국어 이름·주소를 크게** 표시
  - **사용자 실사용 제보로 고친 것**: 휴대폰에서 카카오맵 버튼을 누르면 "카카오맵 연결중입니다" 화면에 멈췄다. 한국인은 아래
    작은 "설치없이 지도보기"를 누르지만, 외국인은 크고 노란 "앱 설치" 버튼을 누르게 된다. 링크 주소(`map.kakao.com/link/search`)가
    휴대폰에서는 앱 연결 화면으로 넘어가는 형식이었다 → 모바일 웹 지도 주소(`m.map.kakao.com/actions/searchView?q=`)로 바꿔
    지도와 출발·도착 버튼이 바로 나오게 했다. 그래도 "앱에서 보기" 팝업이 한 번 뜨는데(바깥을 누르면 닫힘), 이건 막을 수 없어서
    버튼 아래에 "팝업 바깥을 누르면 브라우저에서 계속 볼 수 있다"는 안내를 넣었다.
  - **이어진 피드백: "영문 페이지에서 누르면 영문 지도로 열리면 좋겠다"** — 두 지도를 직접 시험했다.
    네이버 지도 웹은 **휴대폰(브라우저) 언어를 보고 자동으로** 영어·일본어·중국어 화면을 보여준다(휴대폰 언어를 바꿔 접속하면
    화면 글자가 "#NAVER Maps App", "#Save"처럼 바뀜). 주소에 언어를 지정하는 방법은 없었다(`lang=`, `locale=`, `hl=` 등 모두 무시).
    외국인 관광객 휴대폰은 보통 자기 나라 말이라 그대로 두면 된다. 반면 **카카오맵 웹 지도는 한국어만** 있고(메뉴에 언어 설정 없음,
    주소에 언어를 붙여도 그대로) 영어는 앱에서만 된다. 사용자 결정으로 **외국어 화면에서 카카오맵 버튼을 뺐다.**
    선택지 하나를 줄이는 대신, 누르면 "읽을 수 있는 지도"만 남겼다.
  - 1330 관광통역안내전화
  - 장소별: 경복궁 외국어 무료 해설·한복 무료 입장, 국립중앙박물관 평일 외국어 해설·어린이박물관 영어 예약 안내

  "꼭 기억할 3가지"로 올라온다(길치·아이 스위치와 같은 원리). 외국인에게만 필요한 메모는 `audience: "foreign"`으로
  한국어 화면에서 숨긴다. 체크리스트에 9번 "외국인 장벽"을 추가했다(아직 조사 안 한 15곳은 "확인 못함").
- **고르기 쉽게**: 휴대폰 언어를 보고 자동으로 고르고(한국어 휴대폰이면 한국어), 위쪽 버튼(한국어·EN·中文·日本語)으로 바꾼다.
  중국어는 관광객이 가장 많은 간체로 했다.
- **3곳 먼저 시험**: 광화문광장·경복궁·국립중앙박물관(외국인이 많이 가는 곳)만 메모까지 번역하고, 나머지 15곳은 이름·지역·카드
  표시만 번역했다. 메모 번역이 없는 장소는 "아직 한국어만"이라고 알려주고 한국어 메모를 보여준다.
- **사용자 제보: "영문 페이지인데 영문 번역이 안 되어 있어"** (서울어린이대공원). 고장이 아니라 내 설계였다 —
  3곳만 시험 번역하고 나머지는 "번역이 없으면 한국어 그대로 + 작은 안내 한 줄"로 두었는데, 안내는 눈에 띄지 않았고
  검사기도 빠진 번역을 문제로 보지 않았다. 사용자 입장에선 "영어를 골랐는데 한국어가 나오는" 고장으로 보인다.

  이름뿐이었다. 배운 것: **"점진적으로 늘린다"는 만드는 사람의 계획이고, 쓰는 사람에겐 빈 곳이 그냥 고장이다.**
- **사실 확인에서 막힌 것**: 경복궁 외국어 해설 시간이 사이트마다 달랐다(11:00·13:30·15:30 / 10:15·11:30·14:30 등).

  1330 운영 시간도 자료마다 달라(24시간 / 7시~자정) 시간은 빼고 번호만 적었다.

    지도 앱에 "파주 아울렛"만 치면 다른 곳으로 갈 수 있어서, 두 장소 모두에 빨간 주의 카드를 달았다.
  - **같은 2200번 버스인데 두 회사 안내가 다르다.** 신세계는 합정역 8번 출구·약 1시간, 롯데는 1번 출구·약 30분으로 안내한다.

  - **롯데 파주는 건물마다 주소가 다르다**(회동길 390·430, 문발로 302·284). 관광공사 외국어 매장 목록에서 매장 주소를 모아 보다가 알게 됐다.
- **옛 후기와 지금이 다른 정보**
  - 현대 김포는 육아 사이트 후기에 "지하 주차 무료"라고 되어 있다. 그런데 공식 누리집에는 **2026년 2월부터 유료**(구매 금액에 따라 최대 5시간 무료)로 나온다.
  - 후기만 믿었으면 틀린 메모가 됐을 것이다. 그래서 "예전 후기의 무료 주차는 바뀌기 전 내용"이라고 적었다.
  - 배운 것: **숫자(요금·시간)는 후기보다 공식 누리집을 먼저 본다.**
- **매주 쉬는 요일이 아닌 휴무**: 롯데 아울렛은 가끔 전 매장이 쉬는 날(예: 2026년 11월 2일 월요일)이 있다.
  - 지금 구조의 `closedWeekdays`는 "매주 ○요일"만 다룰 수 있다.
  - 날짜 목록 기능을 새로 만드는 대신, 첫 화면 카드에 **"휴점일 확인 필요"** 를 붙이고 고정(pin) 메모로 확인 방법을 안내했다.
  - 이유: 휴점일은 해마다 바뀌어 날짜를 손으로 넣으면 금방 틀린다.
- **대표 사진은 이번엔 넣지 않았다**
  - 관광공사 사진은 5곳 모두 '변경 금지(공공누리 제3유형)'였다.
  - 위키미디어 공용에서는 2장을 찾았다.
    - 파주 사진은 2014년 모습이고 사람이 나온다.
    - 현대 사진은 김포점으로 보이지만 설명에 장소 이름이 없다.
  - 기준(지금 모습, 그 장소만의 모습, 사람 없음)에 확실히 맞지 않아 색 배경으로 두고 사용자에게 확인을 받기로 했다.
- **확인 못함으로 남긴 것**: 신세계 파주의 주차·수유실, 여주의 수유실 위치. 공식 자료를 찾지 못해 지어내지 않았다.
- **같은 날 다시 뺐다 (2026-10-31, 다시 18곳)**
  - 사용자 판단: "아울렛까지 안내할 필요는 없을 것 같다." 이 앱은 처음 가서 헤매기 쉬운 공원·궁궐·체험 공간을 위한 것인데,
    아울렛은 그 중심에서 벗어나 있었다. 대표 사진도 5곳 모두 쓸 수 있는 것이 없어 색 배경으로만 남아 있었다.

  - 배운 것: **"헤매기 쉬운 곳"이라는 조건만으로 장소를 늘리면 앱의 성격이 흐려진다.** 고를 때 "이 앱을 찾는 사람이 여기도 갈까?"를 같이 본다.

### 처음 온 사람용 안내 → 화살표 안내 + 화면 전체 정리 (2026-10-31)
- **문제**: 처음 연 사람은 이게 무슨 앱인지, 위의 "길치예요·아이와 함께" 버튼이 무엇을 바꾸는지 몰랐다.
  웹은 링크를 받고 **장소 화면으로 바로 들어오는 사람**이 많다. 그래서 앱처럼 시작 화면 하나로는 부족했다.
- **1차 시도: 화면 위 텍스트 카드**
  - 가운데 팝업, 버튼 옆 말풍선, 늘 보이는 3단계 설명, 화면 위 카드 4가지를 비교했다. 화면을 가리지 않는 "처음이세요?" 카드를 골라 첫 화면과 장소 화면에 넣었다.
  - 4개 언어도 걱정했지만, 화면 글자를 이미 `ui-text.js`(언어별 글자 사전)에서 바꿔 끼우고 있어서 문제가 없었다.
  - **배포 후 직접 써 본 피드백**: "텍스트가 많아서 불편하다." 설명 문장 3줄을 읽어야 버튼을 이해할 수 있었다.
    사용자는 버튼에 화살표를 그린 스크린샷을 보내며 "이런 팝업 하나면 충분하다"고 했다.
- **2차: 버튼을 직접 짚는 화살표 안내(코치마크)**
  - 장소 화면에 처음 들어왔을 때 한 번만 뜬다. 화면을 어둡게 덮고, 버튼 4곳(길치·아이·대중교통/자차·언어)만 밝게 뚫는다.
    노란 테두리와 화살표, 2~3단어 말풍선만 보여 준다. 아무 곳이나 누르면 닫히고 다시 안 뜬다. 첫 화면에는 띄우지 않는다.
  - **막힌 점 ① 화살표가 다른 버튼을 관통**: 좁은 화면에서는 "대중교통/자차" 바로 아래에 언어 버튼이 있다.
    그래서 곧장 내려가는 화살표가 언어 버튼을 뚫고 지나갔다. 막히면 옆으로 꺾어 빈 줄로 내려가게 했다.
  - **막힌 점 ② 말풍선끼리 길을 막음**: 320px 화면에서는 먼저 놓은 말풍선이 다음 화살표 길을 가렸다.
    버튼이 4개뿐이라 놓는 순서 24가지를 모두 시험해, 겹침이 없는 배치를 고르게 했다. 규칙을 복잡하게 짜는 것보다 단순하다.
  - **막힌 점 ③ 안내가 아예 안 뜨는 경우**: 처음에는 "화면 그리기 신호"를 기다렸다가 띄웠다.
    그런데 이 신호가 백그라운드 탭에서는 오지 않아 안내가 뜨지 않았다. 글꼴을 다 받은 직후 바로 띄우도록 고쳤다.
  - 색은 초록 대신 노랑(`--marker`)을 썼다. 어두운 막 위에서 초록은 잘 안 보였고, 노랑은 이미 포커스 표시에 쓰던 색이라 새 색을 만들 필요가 없었다.
  - 320~985px 화면 × 4개 언어에서 말풍선·화살표 겹침 0건을 자동 검사로 확인했다.
  - **배포 후 추가 피드백**: "메모 상세 내용도 꼭 봐야 하니 펼치기(⌄)도 짚어 달라." 첫 메모의 ⌄에 "눌러서 자세히 보기" 말풍선을 더했다.
    메모 카드는 위쪽 버튼들과 멀리 떨어져 있어 기존 배치 계산에 섞지 않고, 위쪽 배치가 끝난 뒤 ⌄ 바로 아래에 따로 놓았다.
    화면 밖이거나 위쪽 말풍선과 겹칠 자리면 이 말풍선만 숨긴다.
- **3차: "원래 있던 모든 양식"을 다시 보기**
  - 화살표 안내를 만들고 나니 화면 전체의 글자 양도 문제라는 의견이 나왔다. ui-ux-designer 에이전트에게 앱 전체 검토를 맡겼다.
  - 사용자에게 먼저 방향을 물었다. 컨셉은 "지도앱처럼 깔끔하게", 글자는 "많이 줄이기", 고칠 곳은 첫 화면·장소 위쪽·메모·제보 전부였다.
  - **색 시안 3개(블루·그린·인디고)** 를 흰 바탕에 대비 4.5:1 이상으로 계산해 스크린샷으로 비교했다.
    사용자는 **지금 색(연한 종이색 + 숲 초록)** 을 골랐다. 그래서 색은 그대로 두고 배치만 바꿨다.
  - 원칙: **정보는 지우지 않고 접거나 작게 한다.**
    - 첫 화면: 설명을 한 줄로 줄였다. 돋보기가 붙은 검색창이 위에 붙어 있고, 카드를 줄여 한 화면에 더 많이 보이게 했다.
    - 장소 화면 위쪽: 버튼은 보이는 높이만 얇게 하고, 누르는 영역은 44px를 유지했다.
      처음에는 실제로 42px였는데, 실측으로 발견해 고쳤다.
      주소·시간은 한 줄로 줄이고 누르면 펼친다. 외국어 택시 카드는 이름·주소·지도 버튼만 보이고 나머지는 "더 보기"로 접었다.
    - 메모: 분류를 제목 아래 작은 칩으로 옮겨 제목이 덜 꺾이게 했다.
      접혀 있어도 신분증·예약 같은 필수 메모와 주의 메모가 보이도록 **"필수"·"주의" 글자 칩**을 달았다. 전에는 빨간 바탕(색)으로만 구분돼, 색을 잘 못 보는 사람은 알 수 없었다.
    - "꼭 기억할 3가지"가 메모 2개뿐인 장소에서도 3가지로 나오던 것을 발견했다. 개수를 받아 문장을 만드는 방식으로 바꿨다.
    - 제보: "지금 상황"과 "한 줄 제보"를 한 덩어리로 합쳤다.
      메모 출처 설명은 "출처·안내 보기"로 접었다. 사진 촬영자·라이선스는 법적 표시라 항상 보이게 남겼다.
  - 첫 화면의 "30분 먼저 다녀온 AI의 메모" 문구는 기획 의도일 뿐 처음 온 사람에게는 "무슨 30분?"이라는 혼란만 준다고 보고 뺐다.
    AI가 정리·번역했다는 사실은 장소 화면의 출처 안내와 외국어 번역 안내에 그대로 남아 있다.
- **배운 것**: 안내를 "설명 문장"으로 만들면 읽어야 할 글이 하나 더 늘어날 뿐이다.
  버튼을 직접 짚어 주는 것이 처음 온 사람에게 더 빠르다. 첫 버전을 실제로 써 보고 피드백을 받은 덕분에 알게 됐다.

### 링크 미리보기 (2026-10-31)
- **발견**: 카카오톡으로 링크를 보내 보니 미리보기에 "먼저 다녀온 메모"라는 이름과 "여기를 눌러 링크를 확인하세요"라는 기본 문구만 나왔다.
  처음 받은 사람은 이름만 보고는 무엇인지 알 수 없었다.
- **원인**: 메신저는 페이지의 오픈그래프(og) 태그(미리보기용 제목·설명·그림 칸)를 읽는데, 이 칸이 비어 있었다.
- **문구**: 앱 이름은 그대로 두고, 미리보기 제목에 하는 일을 먼저 썼다: "처음 가는 곳, 헤매지 않게 · 먼저 다녀온 메모".
  질문형("지금 여기 가도 될까요?")과 이름+설명 분리도 검토했지만, 제목만 보고도 뜻이 통하는 쪽을 골랐다.
- **그림**: 앱 화면 캡처는 작게 줄면 글자가 안 읽히고, 화면 속 관광공사 사진의 출처 표시까지 따라와야 해서 탈락했다.
  그래서 앱 색으로 길 지도와 갈림길 메모("여기서 오른쪽!")를 **도형으로 직접 그렸다**. 사진이 없어 저작권 걱정이 없다.
  - 처음 그린 그림은 메모에 "여기서 왼쪽!"이라고 썼다. 그런데 정작 길은 오른쪽으로 꺾였고, 메모도 꺾이는 곳이 아닌 직선 위에 붙어 있었다.
    "헤매지 않게"를 말하는 그림이 길을 틀리게 알려 주면 안 되므로, 꺾이는 모퉁이에 표시를 하고 문구를 고쳤다.
  - 그림 원본은 `docs/og-image.html`에 두고 Chrome으로 1200×630 크기로 찍는다. 문구를 바꿀 때 다시 만들 수 있다.
- **한계**: 장소 링크(`?place=`)도 같은 미리보기가 나온다. 장소 화면은 브라우저에서 JavaScript로 그리는데, 메신저는 JavaScript를 실행하지 않기 때문이다.
  장소마다 다른 미리보기를 보여 주려면 서버에서 HTML을 만들어야 해서 보류했다.

### 외국인 여행자 중심으로 방향 전환 — 1단계: 영어를 기본으로 (2026-11-01)
- **왜 바꿨나**: 한국인은 지도 앱 후기·블로그로 이런 정보를 이미 쉽게 얻는다.
  외국인은 휴무·예약·입장 조건·결제 장벽을 한곳에서 영어로 볼 곳이 드물다. 수익화($3 평생 이용권)도 이 사람들을 대상으로 한다.
- **경쟁 조사에서 찾은 빈자리** (서비스 이름은 쓰지 않는다)
  - 혼잡 예측 앱 하나는 "30일 중 가장 여유로운 날"을 추천하는데, 확인한 4곳 중 3곳에서 그날이 **쉬는 날**이었다.
  - 공식 관광 사이트와 여행 예약 사이트는 휴무·예약 안내를 적어 두지만, 여러 페이지에 흩어져 있고 일부는 낡았다.
  - 그래서 "휴무일 표시"만으로는 차별점이 아니다. 차별점은 **휴무를 뺀 한산한 날 계산**, **출입 함정 한곳 요약**, (다음 단계) **그래도 꼭 가야 하는 날 모드**다.
- **문구에 쓰기 전에 사실부터 확인**: 첫 화면에 "열려 있으면서 한산한 날"을 쓰기 전에 코드를 확인했다.
  붐빔 판단(`judgeCrowd`)이 이미 휴무 요일을 빼고 한산한 날을 고르고 있어서, 기능을 과장하지 않는 문구가 된다.
- **"외국인 전용" = 기본값만 바꾸기 (한국어는 지우지 않음)**
  - 택시 기사에게 보여줄 한국어 이름·주소, 표지판의 한국어 표기가 외국인에게도 필요하다. 그래서 한국어 화면과 데이터를 남겼다.
  - 언어 고르는 순서: 주소의 `?lang` → 전에 고른 언어 → 휴대폰 언어 → 영어.

  - 언어 버튼 순서도 EN · 中文 · 日本語 · 한국어로 바꿨다. 버튼을 짚는 화살표 안내가 바뀐 자리에서도 겹치지 않는지 다시 확인했다.

    지금 따로 서버 코드를 만들면 같은 일을 두 번 하게 된다.
- **요청서와 실제 코드가 달랐던 점**: 요청서에는 23곳, `make-og.mjs`·`api/share.js`가 있다고 적혀 있었다.

### 4단계: 영어 검색에 잡히게 — 장소·언어별 페이지를 미리 만들기 (2026-11-01)
- **문제**: 장소 화면은 빈 HTML 에 자바스크립트가 나중에 내용을 그린다. 구글은 실행해서 읽기도 하지만 느리고 불완전하고,
  Bing·네이버·일본·중국 검색엔진은 거의 못 읽는다. 주소도 `/?place=…` 하나라 언어별 페이지가 없었다.
- **비교한 방법**: A. build 때 페이지를 미리 만들기 / B. 방문할 때마다 서버가 만들기(복잡하고 무료 한도를 씀) /
  C. 사이트맵만(구글 외에는 효과 거의 없음). **A를 골랐다**(사용자 승인). 이미 Vercel 이 배포 때마다 `npm run build`를
  돌리고 프로젝트 폴더 전체를 사이트로 내보내고 있어서, "장소 목록 자동 생성"과 같은 원리로 붙일 수 있었다.
- **만든 것**: 18곳 × 4개 언어 장소 페이지 + 언어별 첫 화면 = 76개 페이지, `sitemap.xml`, `robots.txt`.
  - 페이지에는 메모 내용이 미리 들어 있고, 버튼 글자도 그 언어로 바꿔 둔다. 화면은 그 위에서 `app.js`가 평소처럼 다시 그린다.
  - 언어별 짝(`hreflang`)과 대표 주소(`canonical`)를 붙였다. 한국어 페이지도 다른 언어와 똑같이 검색에 노출한다(사용자 결정).
  - 외국어 페이지에는 택시용 한국어 이름·주소도 미리 넣어, 한국어 이름으로 검색하는 사람도 찾게 했다.
  - 만든 페이지는 깃허브에 올리지 않는다. 장소를 고치면 다음 배포 때 페이지도 자동으로 따라 바뀐다.
- **제목·설명은 장소 데이터에서 자동으로**: `경복궁: 화요일은 문을 닫아요`처럼 출입 필수(pin) 메모가 제목에 먼저 들어간다.
  - **막힌 점**: 처음엔 "확인 필요" 표시가 붙은 메모를 모두 제목에서 뺐다. 그랬더니 국립중앙박물관 제목에서 가장 중요한
    "어린이박물관은 예약해야 들어가요"가 빠졌다. 이 메모의 표시는 "예약 오픈 **시각** 확인 필요"라서, 불확실한 건 시각뿐이었다.

  여기에 사용자 본인(9살·6살 딸을 둔 아빠)의 경험이 결정적이었다: "해외에 가도 아이 위주로 일정을 짜지는 않는다."
  아이 동행은 장소 화면의 스위치(아이 메모를 앞으로)로 충분하다고 보고, **누구에게나 같은 순서**를 보여주기로 했다.
- **"비 오는 날 실내" 카테고리 삭제** (사용자 판단): 실내인지는 장소를 보면 알 수 있고, 비 오는 날엔 어차피 실내를 찾게 된다.
  같은 장소가 "아이와 함께"와 "비 오는 날 실내"에 겹쳐 나오는 문제도 줄었다.
  - 지우기 전에 확인해 보니 별마당도서관·DDP·서울스카이는 **이 카테고리에만** 있어서, 그냥 지우면 첫 화면에서 사라질 뻔했다.
    사용자와 상의해 새 카테고리 **"도시 명소"(City landmarks)**로 묶었다. 국립중앙박물관은 "궁궐·역사"에도 넣었다.
  - 메모 안의 "비 오는 날" 안내(예: 경복궁의 우천 시 대안)는 그대로 둔다. 카테고리만 없앤 것이다.

### 6단계: 걸어서 갈 수 있는 이웃 장소 "Nearby on foot" — 틀부터 (2026-11-02)
- **출발점(사용자 경험)**: 런던에서 피카딜리서커스역을 떠나 지하철로 다른 역에 갔는데, 조금 걸었더니 다시 피카딜리서커스가 나왔다.
  지하철 노선도는 거리를 뭉개서 보여준다. 서울도 종로·인사동·시청은 걸어서 몇 분이고, 반대로 명동·남대문에서 남산서울타워는
  가까워 보이지만 오르막이다. 게다가 구글 지도는 한국에서 도보 길안내를 하지 않아 외국인은 "걸어서 몇 분인지" 알기 어렵다.
- **검토한 방법과 고른 이유**
  - 직선거리로 걷는 분을 자동 계산 — 탈락. 직선은 실제 길보다 짧고, 언덕·계단·큰길을 모른다. 숫자를 지어내지 않는다는 원칙에 어긋난다.
  - 지도 API로 보행 시간 받기 — 탈락. 구글은 한국 도보 경로가 없고, 국내 지도 API는 키·약관·비용이 따로 들고 "오르막" 판단은 여전히 사람 몫이다.
  - **혼합(고른 방법)**: build가 좌표로 직선 2km 이내 쌍을 **후보**로만 뽑고(`docs/walk-candidates.md`, 화면에 안 나옴),
    사람이 지도 앱 보행 경로로 확인한 것만 `walkTo`에 적어 화면에 보여준다. 자동은 "어디를 확인할지"만, 숫자는 사람이.
- **설계 결정**
  - 방향이 있는 데이터로 했다. 남대문시장 → 남산서울타워는 오르막, 반대는 내리막이라 같은 쌍이라도 안내가 다르다.
  - 유형은 두 가지뿐: "Skip the subway"(걸어가세요) / "Looks close, but steep"(가까워 보여도 힘들어요). 힘든 쪽은 주의색과
    "아이·어르신과 함께면 시간이 더 걸려요" 한 줄을 자동으로 붙인다.
  - 길안내 앱이 아니므로 지도·경로 그림은 넣지 않고 네이버 지도 링크와 그 장소의 우리 메모 링크만 둔다.
  - 확인된 것이 하나도 없으면 카드 자체가 숨는다. 번역(note) 누락, 없는 장소, 1~60분이 아닌 숫자, 출처·확인 날짜 누락은 build가 막는다.
  - 체크리스트 11번 "걸어서 갈 수 있는 이웃"을 추가하고 24곳 모두 "확인 못함"으로 채웠다. 템플릿에 빠져 있던 10번도 함께 채웠다.
- **확인**: 시험용 항목을 잠시 넣어 영어·중국어·일본어·한국어, 밝은·어두운 화면, 320px 폭에서 확인한 뒤 지웠다.
  일부러 잘못된 분(99분)과 일본어 번역 누락을 넣어 build가 막는 것도 확인했다.
- **보류 (2026-11-02)**: 후보 9쌍을 지도 앱으로 확인하려던 참에 사용자가 멈췄다.
  "네이버 지도에서 검색은 할 수 있지만, 내가 직접 걷지 않는 한 신뢰할 수 있는 데이터인지 의문"이라는 이유였다.
  - 따져 보니 맞는 지적이었다. 지도 앱의 도보 분은 평지 기준으로 계산한 **추정치**이고, 이 기능의 가치는 숫자보다
    "지하철 타지 말고 걸으세요" / "가까워 보여도 힘들어요"라는 **판단**에 있다. 그런데 그 판단(오르막 체감, 큰길 건너기,
    인파)은 걸어 본 사람만 줄 수 있다. 지도 숫자만 옮기면 외국인이 직접 지도를 보는 것보다 나을 게 없고,
    "다녀온 메모"라는 이름과도 어긋난다.
  - 그래서 틀(검사·카드·후보 목록)은 그대로 두고 데이터만 비워 둔다. 확인된 쌍이 0개라 화면에는 아무것도 나오지 않는다.
  - 다시 시작한다면: 사용자가 사진을 찍으러 서울을 다닐 때 후보 쌍을 **직접 걸어 보고** 그 경험을 기준으로 채우는 방식이 맞다.

### 오늘의 판정 "Today's verdict" (2026-11-02)
- **왜**: 장소 화면을 열었을 때 가장 먼저 궁금한 건 "오늘 여기 가도 되나?"다. 그런데 답이 날씨 칩·붐빔 칩·쉬는 날 메모에
  흩어져 있었다. 게다가 "앞으로 30일 중 가장 여유로운 날"을 추천하는 서비스들은 쉬는 날을 빼지 않아, 사람이 없어 점수가
  낮은 **휴무일을 추천**하는 일이 생긴다. 그래서 신호등 한 줄로 답하되, 휴무를 가장 먼저 거른다.
- **규칙 (위에서부터 먼저 맞는 것)**: 빨강 쉬는 요일 → 노랑 쉬는 날이 정해져 있지 않은 곳 → 노랑 붐빔 상위 20% 또는
  3시간 안 비·눈 → 초록 → 회색.
  - **자료가 없으면 초록 금지**: 붐빔 예측이 없거나 날씨를 못 받으면 "오늘 열어요"(회색)까지만 말한다. 모르는 것을
    "가기 좋은 날"이라고 하면 지어낸 것과 같다.
  - **카드 글자를 읽어서 판단하지 않는다**: "후원 예약 필요" 같은 notice 글자를 해석하면 문구만 바꿔도 판정이 달라진다.
    그래서 `reservation`("all"/"part")과 `irregularClosure`를 place.json에 따로 두고 build가 검사한다. 예약은 창덕궁(후원)·
    국립중앙박물관(어린이박물관)처럼 **일부만** 예약인 곳이 있어 "all/part"로 나눴다(사용자 선택). 불규칙 휴무는 남대문시장 1곳.
  - **공휴일은 추측하지 않는다**: 공휴일 목록이 없어서, 쉬는 요일과 공휴일이 겹칠 때 여는지는 판단하지 않고 쉬는 요일
    기준으로만 판정한다.
- **중복 없애기**: 붐빔 칩("오늘은 쉬는 날이에요", "덜 붐비는 날")을 판정 카드 안으로 합쳤다. 쓰다 보니 한산한 날에
  "오늘 한산할 듯 · 앞으로 30일 중 한산한 편"이 같은 말을 두 번 해서 한 줄만 남겼다. 예전에는 붐빔 예측이 없는 장소는
  쉬는 날이어도 아무 표시가 없었는데, 판정은 쉬는 요일을 먼저 보므로 이 구멍도 메워졌다.
- **노랑이면 다음 행동으로**: "가도 돼요, 계획은 세우고"일 때 이미 있는 "I'm going anyway today" 모드를 켜는 링크를 단다.
- **구조**: 판정은 `verdict.js`의 순수 함수 `verdict(place, date, crowdDays, weather)`. 날짜를 인자로 받으므로 첫 화면
  지역별 보기·날짜 고르기에서도 그대로 쓴다. 기존 `judgeCrowd()`·`kstToday()`는 새로 만들지 않고 이 파일로 옮겼다.
- **시험**: `scripts/test-verdict.mjs`(npm run build에 포함) 23개 통과 — 경복궁 화요일·창덕궁 월요일 빨강, 덜 붐비는 날에
  쉬는 요일이 끼지 않음, 붐빔 자료 없음·빈 목록·날씨 못 받음 → 회색, 붐빔 상위 20%·비 → 노랑, 4시간 뒤 비는 초록,
  irregularClosure → 노랑, 한국 시간 자정 직전·직후(UTC 14:59:59 / 15:00:00), 4개 언어 글자 빠짐 없음.
  화면은 320px·밝은/어두운·4개 언어에서 확인했다.

  → 품질 기준에 "대표 사진은 그 장소만의 모습이어야 한다"와 "사람이 알아볼 수 있게 나오면 쓰지 않거나 지운다"를 추가했다.
- **결국 찾은 곳: 한국관광공사 관광정보 API**. 위키미디아에는 서울숲다운 사진이 없었다(30장 + 항공 사진까지 확인). 관광공사
  관광정보 API는 관광지마다 공식 사진 목록과 **사진별 저작권 유형**을 함께 준다. 서울숲은 15장이 모두 공공누리 제1유형(출처만
  밝히면 자유 이용)이었다. 사진을 내려받지 않고 화면에 모아 보는 임시 미리보기 페이지를 만들어 사용자와 같이 골랐고,
  "도심 속 큰 숲 + 그 너머 고층 건물"이 한눈에 보이는 전경을 골랐다. 사용자 반응: "좋은 사진 엄청 많다."
  - 막힌 곳: 국문 버전 대신 **영문 버전**이 신청돼 처음엔 "등록되지 않은 서비스키"가 나왔다. 영문 버전도 같은 공식 사진을
    주기 때문에 그대로 썼다. 장소를 늘릴 때마다 이 API로 대표 사진 후보를 찾을 수 있게 됐다.
- **사진을 찾다 발견한 주소 오류**: 광화문광장·용산가족공원도 관광공사 사진으로 바꾸려고 조회하다가, 관광공사의 용산가족공원
  주소가 **"서빙고로 185"**인데 앱에는 **"서빙고로 137"**로 돼 있는 걸 발견했다. 여러 자료로 확인해 보니 185가 맞았다.
  시험판 때부터 있던 오류였다. 주소는 지도 앱에 그대로 검색하는 정보라 처음 가는 사람을 엉뚱한 곳으로 보낼 수 있다.
  주소와 날씨 좌표를 고치고, 품질 기준의 "올리기 전 확인"에 **주소·좌표를 공식 자료와 맞춰 보기**를 추가했다.
- **라이선스 때문에 바꾸지 않은 사진**: 용산가족공원의 관광공사 사진 10장은 모두 공공누리 제3유형(변경 금지)이었다. 우리 화면은
  사진을 잘라 쓰고 어두운 막을 덮어서 "변경"에 해당할 수 있어, 잘라 써도 되는 지금의 위키미디아 사진을 그대로 뒀다.
  광화문광장은 1유형 사진 7장 중 크리스마스 마켓 같은 행사 사진을 빼고, 사용자가 이순신 장군 동상 사진을 골랐다.
- **일산 MBC**: 위키미디아의 세로 사진(2014) 한 장뿐이라, "MBC" 로고와 송신탑이 보이도록 가로로 잘라 썼다. 처음엔 로고가
  장소 이름 글씨 뒤에 가려져 위치를 다시 맞췄다.
- **화면**: 사진 아래쪽을 어둡게 처리해서 흰 글씨가 잘 읽히게 했고, 사진마다 보여줄 위치(`position`)를 정해
  광장·숲이 보이도록 했다. 사진이 없는 장소는 높이만 키우고 은은한 색 배경을 깐다.

### 배포: GitHub + Vercel
- **방식**: 코드를 깃허브 공개 저장소에 올리고 Vercel이 그 저장소를 지켜보게 했다. 코드를 올릴 때마다
  `npm run build`(장소 목록 생성 + 형식 검사)를 거쳐 자동으로 다시 배포된다. 장소 파일에 실수가 있으면
  검사에서 걸려서 **망가진 사이트가 올라가지 않는다**.
- **인증키**: `.env`는 깃허브에 올리지 않고 Vercel 설정 화면의 환경변수(Environment Variables)에만 넣었다.
  배포 후 `/.env` 주소가 404(없음)인지 확인했다.
- **Output Directory를 `.`로 정한 이유**: 이 프로젝트는 빌드해도 별도 결과 폴더가 생기지 않는다. 비워 두면
  Vercel이 다른 폴더를 찾을 수 있어서, "프로젝트 폴더 전체가 사이트"라고 명시했다.
- **막혔던 곳**: Vercel이 깃허브 저장소 목록에서 새 저장소를 못 봤다. 예전에 다른 저장소 하나만 허락해 뒀기 때문이다.
  깃허브의 Vercel 앱 설정에서 이 저장소만 추가로 허락했다(모든 저장소를 열지는 않음).
  배포 버튼을 누르자 이메일 코드로 본인 확인을 한 번 더 요구했다(비밀 값을 저장할 때의 보안 절차).
- **배포 후 확인**: 휴대폰 크기 화면에서 장소 목록, 서울숲 메모, 실제 기상청 날씨가 모두 나오는 것을 확인했다.

### 지키는 원칙
- 네이버 지도 리뷰나 인스타그램은 크롤링(자동 수집)하지 않는다. 약관 위반이다.
- 메모별 출처가 없는 정보는 지어내지 않고 비워 둔다. 시험판 메모 12개는 `source`가 비어 있고,
  장소 전체 출처만 화면 아래에 표시한다.
- API 인증키는 코드에 쓰지 않고 `.env` 파일로 분리한다 (3단계부터 적용).
